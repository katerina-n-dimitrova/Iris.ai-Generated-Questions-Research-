DocBank · generated-question enrichment retrieval

Does generated-question-only retrieval work on layout-heavy scientific text (arXiv/LaTeX documents), and does raising questions/chunk (q5→q15) justify its cost? Synthetic Q&A over 15 full documents are the queries; a question hit returns its parent chunk.

1 · Dataset inspection summary

DocBank (Li et al., 2020 · arXiv:2006.01038)

DocBank is built from arXiv/LaTeX documents with weak supervision. Each page ships as a token-level annotation file: every line is token · x0 y0 x1 y1 · R G B · font · label. We reconstruct text per layout element (merging consecutive same-label tokens) and drop graphical placeholder tokens (##LTLine## etc.).

  • Existing QA / relevance / evidence labels: none — DocBank is a layout dataset with no questions, answers, or relevance judgements. We therefore generate a synthetic Q&A evaluation set (§7).

2 · Page-level or document-level?

page-level source, grouped into documents

DocBank is distributed page-level (one annotation file per page). The parquet mirror (maveriq/DocBank) is token-level and anonymised (no doc/page id), so pages cannot be grouped there. We instead use the original release, whose filenames encode the arXiv document id + page number (…1401.0091…_arxiv_7.txt), and group pages into full documents. Only the zip central directory + the selected documents' small .txt files are pulled via HTTP range requests — never the 3.17 GB archive.

3 · QA / evidence labels?

none native → synthetic eval built

DocBank has no QA pairs and no relevance/evidence labels. We build a synthetic evaluation set (§7): each question is grounded in exactly one chunk, which serves as the single gold relevance label for retrieval scoring.

5 · Chunking strategy & statistics

layout-aware, token-budgeted

Flow text (paragraph / section / list / abstract / small inline equations) is packed into ~500-token chunks (cap 600, ~100 overlap). Tables, captions and large display equations are kept as their own retrieval units, combined with the current section heading and a snippet of preceding text (surrounding explanation). Chunks partition the primary content so each synthetic-QA gold chunk is unambiguous.

12 · Does generated-question-only retrieval work for DocBank?

interpretation — questions-only competitive

Best questions-only condition q13 reaches nDCG@10 0.7198 vs the chunk-text baseline 0.6458 (+0.0740); fused = 0.6933.

  • More questions ⇒ better, monotonically: nDCG@10 q5 0.707 → q10 0.713 → q13 0.720 → q15 0.718. Each added question is its own vector, so more coverage only helps — no dilution.
  • Questions-only matches/beats the chunk text here: on layout-heavy scientific text the chunk vector is a strong single representation, but generated questions add lexical entry points that help most at higher recall depth.
  • Cost: q-conditions use several× the embeddings of the baseline; each question vector is tiny (no chunk text stored) so index size stays modest.
  • Caveat (synthetic eval): both the eval questions and the enrichment questions are LLM-generated from the same chunks, which can flatter questions-only retrieval — a generated enrichment question may closely mirror an eval question. Treat absolute numbers as optimistic; the relative q5→q15 and vs-baseline trends are the signal.
  • Layout note: this sample is equation-heavy / table-sparse (3 tables), so table retrieval is under-tested; equation and caption units are well represented.

13 · Recommendation for the next experiment

where to go next
  • Use fused, not questions-only: keep the chunk vector and add question vectors — pure questions-only discards the strong chunk representation; fusion keeps its precision and adds the questions' recall.
  • Question count: gains grow to q13 then flatten; pick the smallest count on the plateau to save generation/embedding cost.
  • Real evidence labels: replace synthetic QA with a human- or citation-grounded eval to remove the generator-overlap bias; or evaluate on PeerQA-style real questions over DocBank layout.
  • Layout-balanced sample: deliberately sample documents with more tables/figures (later arXiv categories) so table/figure retrieval is properly tested — this math-paper sample is equation-heavy and table-sparse.
  • Exploit layout type: route or weight retrieval by element type (equation / table / caption) and generate type-specific questions, rather than one generic doc2query prompt.

Analysis

chunk size vs question enrichment
  • Do larger chunks benefit from more questions? Yes — the best fixed count rises with size (200t→13q, 400t→13q, 600t→15q, 800t→15q). More questions help most where a chunk holds more distinct facts.
  • Is q10 a sweet spot across sizes? q10 is the top fixed count in 0/4 sizes; DocBank chunks are small/dense so the plateau often sits at 13, 13, 15, 15 questions respectively.
  • “Bigger chunk ⇒ more questions” (adaptive length) vs fixed q10: adaptive length wins (nDCG 0.664 vs 0.639) — and at avg 5.98 q/chunk (fewer than 10), so it is also cheaper.
  • Do smaller chunks need fewer questions? Yes — a 200-token DocBank chunk holds few facts, so the LLM makes fewer grounded questions and extra requested ones become near-duplicate embeddings; small chunks saturate earliest.
  • Do larger chunks get too broad/noisy? Larger chunks lift recall (the right chunk is easier to hit) but blur rank-1; more questions give a big chunk several sharp entry points, which is why bigger chunks gain most from more questions.
  • Gains from size, count, or both? Chunk size alone moves baseline nDCG@10 by ~0.042; question count within a size by up to ~0.116. Question count is the larger lever here, but they interact.
  • Worth the cost? Generated questions cost N× embeddings + a one-off LLM pass. On DocBank (synthetic eval) they clearly help; the smallest count on each size's plateau captures most of the gain — going to q15 rarely pays.
Caveat
The eval questions and enrichment questions are both LLM-generated from the same chunks, which flatters questions-only retrieval (as in the single-size DocBank run). Treat absolute levels as optimistic; the size×count shape is the finding.

Recommendation

one practical setup
  • Best fixed setup: chunk size 600 tok with 15 questions/chunk (nDCG@10 0.7103). Overall best across all conditions: chunk_size_600_q15 (0.7103).
  • Adaptive rule (“bigger ⇒ more”): adopt length-based allocation — it beats fixed q10 at lower cost (cap 15, floor ~4).
  • Length vs density: length-based is simpler and competitive; density needs only cheap regex signals (numbers, symbols, Table/Eq refs).
  • Precision: for rank-1-critical use keep the chunk vector and fuse with the question vectors instead of going questions-only.
  • Next: replace synthetic QA with real/citation-grounded eval to remove generator overlap, and sample table/figure-rich documents to stress layout retrieval.
