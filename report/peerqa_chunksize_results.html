PeerQA · chunk size × generated-question enrichment

Does the amount of generated-question enrichment needed for retrieval depend on chunk size and/or information density? Questions-only doc2query retrieval (embed only generated questions; a hit returns the parent chunk), swept across 4 chunk sizes and fixed vs adaptive question counts.

Experimental setup

same PeerQA subset & retrieval setup as the questions-only experiment

PeerQA reviewer questions are the queries; gold = author-annotated evidence sentences mapped onto whichever chunk(s) contain them. Retrieval embeds only generated questions (each mapped to its parent chunk); a chunk-text dense index is the baseline, and a fused (chunk-vector ⊕ best-question) variant is included for the adaptive testbed.

  • Subset: 15 papers (same selection as before).
  • Embedder: huggingface:Octen/Octen-Embedding-0.6B:dim1024. LLM: gpt-4o-mini, grounded diverse-subtopic prompt.
  • Chunk sizes: 200 / 400 / 600 / 800 tokens, overlap ~22% (45 / 90 / 125 / 175). Adaptive strategies run on a separate section-aware variable-size chunking (~100–800 tokens).
  • Question pool: up to 15 grounded questions generated once per chunk (cached); fixed q5/q10/q13/q15 and adaptive allocations are first-k slices.
  • Metrics: Hit@1/5/10, MRR, nDCG@10, + query latency, generation time, encode time, #questions, #embeddings, index size.

Analysis

chunk size vs question enrichment
  • Do larger chunks benefit from more questions? Yes — the best fixed count rises with size (200t→10q, 400t→15q, 600t→13q, 800t→15q). More questions help most where a chunk holds more distinct facts.
  • Is q10 still a sweet spot across sizes? q10 is the top fixed count in 1/4 sizes; elsewhere the best sits at 10, 15, 13, 15 questions respectively — q10 is a solid default but not universally optimal.
  • Does adaptive beat fixed q10? Yes — best adaptive nDCG@10 0.537 vs fixed q10 0.501 at matched average budget. Reallocating a fixed question budget toward denser/longer chunks pays off.
  • Do smaller chunks need fewer questions? Yes structurally — a 200-token chunk holds few distinct facts, so the LLM produces fewer grounded questions and extra requested questions become near-duplicates that add embeddings without recall; small chunks saturate earliest.
  • Do larger chunks get too broad/noisy? Larger chunks raise recall (the right chunk is bigger, easier to hit) but blur rank-1 precision; questions counter this by giving the big chunk several sharp entry points, which is why big chunks gain the most from more questions.
  • Gains from size, count, or both? Across baselines, chunk size alone moves nDCG@10 by ~0.122; within a fixed size, question count moves it by up to ~0.158. Question count is the larger lever here, but they interact — the best config needs both tuned.
  • Is the extra generation/indexing worth it? Generated questions cost N× the embeddings and a one-off LLM pass; they buy recall (Hit@5/10) more than rank-1 precision. Worth it when recall at depth matters; if only Hit@1 matters, the chunk-text (or fused) index is cheaper and stronger.

Final recommendation

one practical setup for future runs
  • Best overall: plain 800-token chunk-text retrieval (baseline) is the single strongest and cheapest index — nDCG@10 0.6048 at 8.4 MB. On this subset, using a larger chunk beats adding generated questions on nDCG@10.
  • Best fixed chunk size + question count: if you do enrich, use the largest chunk with the most questions — chunk_size_800_q15 (size 800, 15 q/chunk), nDCG@10 0.5602; smaller chunks and fewer questions are strictly worse.
  • Adaptive rule: if adopting adaptive counts, prefer the length-based rule (cap 15, floor ~4). It concentrates questions on denser/longer chunks and sparse ones get fewer, trimming wasted near-duplicate questions.
  • Length vs density: length-based is the simpler, competitive choice here; density needs only cheap regex signals (entities, numbers, metric terms, table/figure refs).
  • Is the complexity worth it vs fixed q10? Yes — adaptive beats q10 by 0.036 nDCG@10 at matched budget; revisit at full-corpus scale before committing to adaptive machinery.
  • Precision vs recall: for rank-1-critical use, keep the chunk vector and fuse it with the generated-question vectors rather than going questions-only — fusion recovers the precision that pure questions-only sacrifices while keeping its recall.
