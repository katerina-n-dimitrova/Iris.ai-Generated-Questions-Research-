Context-Enriched RAG — Results Summary

Does adding context before embedding improve Retrieval-Augmented Generation? Baseline vs. context-enriched, across four document types.

What this experiment tested

We compared two ways of preparing documents for a RAG system, on four kinds of data.

  • Baseline: embed the raw text only (a sentence, a passage, a table row, or chart text).
  • Enriched: embed the raw text plus added context — titles, position, column headers, keywords, and short generated summaries.

The four datasets

  • SciFact — structured scientific text (abstracts)
  • NFCorpus — unstructured biomedical text
  • WikiTableQuestions — tables
  • ChartQA — charts / graphs

Embeddings: Octen/Octen-Embedding-0.6B (local). Vector store: Chroma Cloud. Answer model & grader: gpt-4o-mini via LangChain (traced to LangSmith). Enrichment here used cheap heuristic summaries/keywords (no LLM).

ChromaDB takeaways

  • helps Text (SciFact, NFCorpus): enrichment improved ranking — SciFact better on every metric; NFCorpus MRR +0.08, Hit@5 +0.03.
  • hurts Tables (WikiTableQ): enrichment lowered every metric — the boilerplate diluted the distinctive cell values.
  • no signal Charts (ChartQA): near-random both ways — ChartQA has no usable text without an image/OCR step.
  • Cost: enrichment made chunks 1.5–3.7× bigger and indexing up to 3× slower (WikiTableQ 426s vs 139s), but online query latency barely changed (~175–195 ms, dominated by the Chroma Cloud round-trip).

Latency takeaways

  • Enrichment's cost is almost entirely OFFLINE. Larger chunks slowed encoding by 1.5–3.3× per chunk; the worst case was Tables, where total index build time jumped 3× (139s → 426s).
  • Online query latency barely moved (~215–237 ms either way). The query itself is the same length in both conditions, so embedding the query takes the same time.
  • The dominant online cost is the Chroma Cloud round-trip (~175–195 ms of search), not the local embedding (~40–52 ms). A self-hosted/local Chroma would cut most of this.
  • Embedding speed scales with content length. NFCorpus is slowest per chunk (long passages, ~89–134 ms); ChartQA is fastest (almost no text).

Summary findings — in plain English

The big finding

Adding context before embedding helped the system find the right documents (for text), but made the final answers worse everywhere. In other words, better retrieval did not lead to better answers — the extra context that helped search became noise that confused the answer-writing step.

1. It depends a lot on the type of document

  • Plain text (science & biomedical): enrichment helped retrieval. Adding the title, keywords, and a short summary made the right documents rank higher.
  • Tables: enrichment hurt retrieval. Turning a clean row into a wordy sentence buried the exact values a table question needs to match.
  • Charts: we couldn't test it fairly — ChartQA gives images with no text, so there was almost nothing to embed without an image-reading (OCR) step.

2. Enrichment is not free

  • Enriched chunks were 1.5–3.7× larger, so building the index took up to 3× longer.
  • But it barely affected live query speed — most of the ~0.2s per query is just the network trip to Chroma Cloud, which is the same either way.

3. The answers got worse with enrichment

  • On every dataset, the enriched setup produced less faithful and less relevant answers.
  • The likely reason: our enrichment used simple keyword lists and extractive summaries (no AI). Those fragments cluttered the context, and the answer model picked up the clutter.

What this means

  • Context enrichment is a trade-off, not a free win. It can improve search for text, costs more to build, and — with low-quality enrichment — can damage answer quality.
  • Match the technique to the data type. Helpful for prose, harmful for tables, untestable for charts without OCR.
  • The quality of the added context matters most. The natural next experiment is to repeat this with LLM-generated summaries instead of keyword dumps, which may reverse the answer-quality drop.

Honest caveats

  • Small samples (100 SciFact / 30 NFCorpus / 300 WTQ / 300 ChartQA queries).
  • Enrichment was heuristic (no LLM) — results may differ with AI-generated context.
  • ChartQA needs a multimodal OCR step to be a fair test.
  • Answer grades come from an LLM judge (gpt-4o-mini), which is useful but noisy.

Related work

One closely related study with a finding that frames our results.

Anthropic — "Contextual Retrieval" (2024)

Same core idea as this project: add context to each chunk before embedding. The key difference is they used an LLM to generate coherent, document-aware context for every chunk (not keyword lists).

  • Contextual embeddings cut the top-20 retrieval failure rate by 35% (5.7% → 3.7%).
  • Combined with contextual BM25: 49% reduction; adding reranking: 67%.

Why it matters here: their high-quality LLM context strongly improved retrieval, while our cheap heuristic context only helped text retrieval modestly and hurt answer quality. Both point to the same lesson — the quality of the added context is decisive — and motivate our recommended next step: re-run enrichment with LLM-generated summaries.
